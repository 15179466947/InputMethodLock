## 🔴 P0-1　配置加载吞掉 `chinese` 模式（重启后失效）

**位置**：`src/Config.cs:52`

```csharp
case "Mode": cfg.Mode = val == "layout" ? "layout" : "english"; break;
```

`Save()` 会正确写出 `Mode=chinese`，但 `Load()` 的三元表达式只识别 `layout`，**其余一律回落 `english`**。

**后果**：用户在托盘菜单选「中文锁定」→ 写入配置 → 下次启动被读成 `english` → 静默退回英文锁定。用户会认为"中文锁定没用 / 设置不保存"。

**修复**（顺手把字符串魔法值收敛为白名单校验）：

```csharp
case "Mode":
    string m = val.ToLowerInvariant();
    cfg.Mode = (m == "layout" || m == "chinese") ? m : "english";
    break;
```

> 根因是 `Mode` 用了裸字符串而非枚举。若把 `LockMode` 从 `ImeLocker.cs` 提到 Config 层复用（枚举 + `Enum.TryParse`），这类"加新模式忘了改一个分支"的问题会从根上消失。当前 `LockMode` 已有 `English/Chinese/Layout` 三个成员，正好对得上。

## 🔴 P0-2　托盘图标 GDI 句柄泄漏 + 双重 `GetHicon`

**位置**：`src/TrayIcon.cs:373-378`

```csharp
_currentIcon = Icon.FromHandle(bmp.GetHicon()).Clone() as Icon;
DestroyIcon(bmp.GetHicon());          // ← 第二次调用，产生的是另一个新句柄
```

三个问题叠加：

1. `bmp.GetHicon()` 被调用两次 → 生成 **两个** GDI 图标句柄，只销毁了第二个，第一个永久泄漏。
2. `Icon.FromHandle(...)` 产生的中间 Icon 未释放。
3. `_tray.Icon = MakeIcon(...)` 覆盖了旧 Icon，旧值从不 `Dispose`。

每次状态切换泄漏 2+ 个 GDI 句柄。Windows 每进程 GDI 句柄上限默认 10000，频繁开关锁定会缓慢累积，表现为托盘图标变白/程序卡死。

**修复**（对比 `AppResources.CreateIcon` 的写法就是对的，照抄即可）：

```csharp
IntPtr hIcon = bmp.GetHicon();
try
{
    using (Icon tmp = Icon.FromHandle(hIcon))
        _currentIcon = (Icon)tmp.Clone();
}
finally { DestroyIcon(hIcon); }
```

并在 `SyncLockStateUi` 中释放旧值：

```csharp
Icon oldTray = _tray.Icon;
_tray.Icon = MakeIcon(_locker.Enabled);
if (oldTray != null) oldTray.Dispose();
```

> 另外 `MakeIcon` 末尾 `return (Icon)_currentIcon.Clone();` 又多克隆一份，而 `_currentIcon` 除了在 `MakeIcon` 开头被 `old` 接住外从不使用——两份图标、两份 GDI 资源，建议直接返回 `_currentIcon` 并让调用方负责生命周期。

## 🟠 P1-1　热键解析失败时静默注册默认热键

**位置**：`src/HotkeyHook.cs:80-90`

```csharp
public static uint ParseKey(string name)
{
    try { return (uint)(int)Enum.Parse(typeof(Keys), name, true); }
    catch { return (uint)Keys.Oemtilde; }   // ← 应该返回 Keys.None
}
```

配置文件被手改坏、或写入非法键名时，解析失败会**兜底成 `Oemtilde`**，于是静默注册了 `Ctrl+\`` 热键。用户本意是"这个热键不生效"，实际却是"默认热键偷偷生效"。`name == null\` 时同理。

**修复**：`catch { return (uint)Keys.None; }` —— 与 `ApplyHotkey()` 里 `key == Keys.None → Unregister()` 的语义才自洽。

## 🟠 P1-2　键盘钩子回调无异常保护（崩溃风险）

**位置**：`src/ImeWatcher.cs:86-110`

`KeyboardProc` 是低级钩子回调，由系统从 native 层调用，回调链是 `Fire() → OnImeChanged() → ImeLocker.Enforce() → 多个 P/Invoke`。其中任何一环抛异常，**异常无法跨 native 边界传播回 .NET**，行为未定义，实践中通常直接终止进程。

同理 `OnWinEvent`（`SetWinEventHook` 回调）也是 native 回调。

**修复**：整个回调体包 try/catch，且**必须**保证 `CallNextHookEx` 一定被调用（否则全局键盘输入被卡死，比崩溃更糟）：

```csharp
private IntPtr KeyboardProc(int nCode, IntPtr wParam, IntPtr lParam)
{
    try { /* 现有逻辑 */ }
    catch { }
    return CallNextHookEx(_kbdHook, nCode, wParam, lParam);
}
```

## 🟠 P1-3　Mutex 创建无异常保护 + `Global\` 前缀偏激进

**位置**：`src/Program.cs:15`

```csharp
using (var mutex = new Mutex(true, MutexName, out createdNew))
```

- `Global\` 命名空间在受限环境（组策略、部分安全软件、容器化会话）下创建会抛 `UnauthorizedAccessException`，而这里**没有 try/catch** → 未处理异常 → 程序起不来，连错误提示都看不到（catch 在 `Application.Run` 外层包住了，但 mutex 构造在 try 之外，实际在 `using` 头，确实不在 try 内）。
- `Global\` 意味着**跨用户会话**互斥。快速用户切换 / 远程桌面多会话时，B 用户会因 A 用户的实例而无法启动，这未必是期望行为。

**建议**：改用 `Local\InputMethodLock_SingleInstance`（单用户会话内互斥，符合"托盘常驻工具"的语义），并加 try/catch 兜底：

```csharp
Mutex mutex = null;
bool createdNew = false;
try { mutex = new Mutex(true, "Local\\InputMethodLock_SingleInstance", out createdNew); }
catch { createdNew = true; }   // 拿不到锁就按单实例放行，不要因此阻止启动
```

## 🟠 P1-4　每 30ms 一次 `Process.GetProcessById`（高频开销）

**位置**：`src/ImeLocker.cs:78-82` → `src/ImeApi.cs:83-104`

```csharp
IntPtr hwnd = ImeApi.GetForegroundWindow();     // 已拿到 hwnd
string proc = ImeApi.GetForegroundProcessName(); // 内部又调一次 GetForegroundWindow + GetWindowThreadProcessId + Process.GetProcessById
```

`Process.GetProcessById` 会打开进程句柄、查询性能计数器，属于重量级调用。以 30ms 计约 **33 次/秒**，且绝大多数时候前台进程根本没变——纯浪费。附带问题：`GetForegroundProcessName()` 内部重复了一次 `GetForegroundWindow()`，两次采样之间前台窗口可能已变化，理论上存在 hwnd 与进程名不匹配的竞态。

**修复**：pid → 进程名做缓存（前台窗口变化不频繁）：

```csharp
private static uint _cachePid;
private static string _cacheName;
private static int _cacheTick;

public static string GetForegroundProcessName(IntPtr hwnd)
{
    uint pid;
    GetWindowThreadProcessId(hwnd, out pid);
    if (pid == 0) return null;
    if (pid == _cachePid && Environment.TickCount - _cacheTick < 1000) return _cacheName;
    // ... 解析并写入缓存
}
```

## 🟠 P1-5　`ForceEnglishMode` 语义与 `IsEnglishMode` 相反（状态误导）

**位置**：`src/ImeApi.cs:107-122` vs `src/ImeApi.cs:144-158`

```csharp
// ForceEnglishMode
if (hIMC == IntPtr.Zero) return false;   // 无 IME 上下文 → 判失败

// IsEnglishMode（同一个类，同一场景）
if (hIMC == IntPtr.Zero) return true;    // 无 IME 上下文 → 纯英文键盘，算英文
```

两个函数对"没有 IME 上下文"给出了**相反**的判断。后者是对的：前台是纯英文键盘布局时压根没有 IME，用户目标（英文）已经达成了。

**后果**：用户切到美式英文键盘后，托盘状态被 `UpdateState(false)` 置为"未锁定"，图标灰化、设置窗口取消勾选——**明明锁着却显示没锁**。

**修复**：`ForceEnglishMode` 中 `if (hIMC == IntPtr.Zero) return true;`

## 🟡 P2-1　布局锁定静默降级为英文锁定

**位置**：`src/ImeLocker.cs:89`

```csharp
if (_mode == LockMode.Layout && _targetHkl != IntPtr.Zero) { ... }
else if (_mode == LockMode.Chinese) { ... }
```

`ParseLayoutStorage` 失败返回 `IntPtr.Zero`，此时布局锁定会**静默退化成英文锁定**。用户以为在锁布局，实际在锁中英状态。

## 🟡 P2-2　热键注册失败无任何反馈

**位置**：`src/TrayIcon.cs:227`、`src/HotkeyHook.cs:25`

`RegisterHotKey` 返回 bool，但 `Register()` 的返回值被丢弃，`ApplyHotkey()` 也不检查。热键被别的软件（如输入法自身、IDE）占用时，`initOk` 仍为 `true`，气泡提示"启动成功"，用户按热键没反应却不知道为什么。

**建议**：注册失败时通过气泡提示告知"热键 Ctrl+\` 被占用，请在设置中更换"。

## 🟡 P2-3　热键输入框 `_capturing` 永不复位

**位置**：`src/SettingsForm.cs:99, 275`

```csharp
_txtHotkey.Enter += delegate { _capturing = true; };   // 只设 true
// 没有 Leave 事件复位
private void OnHotkeyKeyDown(object sender, KeyEventArgs e)
{
    e.SuppressKeyPress = true;   // ← 无论是否 capturing 都先吞键
```

一旦焦点进过热键框，`_capturing` 就永远是 `true`，此后该控件内的所有按键都被吞掉并处理（包括误触的 Delete 会清掉热键配置）。

**修复**：加 `_txtHotkey.Leave += delegate { _capturing = false; };`，并把 `SuppressKeyPress` 移到 `_capturing` 判断之后。

## 🟡 P2-4　文档与代码不一致（轮询周期）

- `README.md:59`：「锁定采用 **150ms 轮询兜底**」
- `README.md:8`：「**30ms 轮询** + 变化监听」
- `ImeLocker.cs:33`：`_timer.Interval = 30`
- `ImeWatcher.cs:7` 注释：「30ms 轮询之外的第二道防线」

同一份 README 里 30ms 与 150ms 自相矛盾。另外，既然已有**低级键盘钩子 + WinEvent 双事件源**做即时响应，30ms 轮询其实过于激进——三重叠加意味着每秒 33 次跨进程 `ImmGetContext`/`ImmGetConversionStatus`。建议轮询放宽到 100~150ms（README 原本写的就是 150ms），靠事件保证响应速度，CPU 占用显著下降。

## 🟡 P2-5　中文锁定兜底布局只查"已加载"列表

**位置**：`src/ImeApi.cs:63` + `src/TrayIcon.cs:193`

`FindLayoutByLanguage` 基于 `GetKeyboardLayoutList`，该 API 只返回**当前会话已加载**的布局（通常 2~4 个）。若系统装了中文输入法但本次会话从未激活过，列表里就没有，`_chineseHkl` 为 `Zero` → 中文锁定在英文键盘上无法自动切回中文。

**建议**：找不到时主动 `LoadKeyboardLayout("00000804", KLF_ACTIVATE)` 加载一次。

## 🟡 P2-6　缺少全局异常兜底

`Program.cs` 只 try 了 `Application.Run` 的构造期异常，WinForms 消息泵内（Timer.Tick、菜单点击、钩子回调）的异常会走默认的"未处理异常"对话框或直接崩掉。托盘常驻工具很忌讳静默退出。

**建议**：

```csharp
Application.ThreadException += (s, e) => { /* 记日志 + 气泡提示 */ };
AppDomain.CurrentDomain.UnhandledException += (s, e) => { /* 记日志 */ };
```

配合一个可选的调试日志（写到 `%AppData%\InputMethodLock\debug.log`，设置里开关），排查这类跨进程输入法问题会容易得多。

1. **死代码**：`_icon16`（`TrayIcon.cs:61,88` 创建后从未使用，且未 Dispose）、`ImeApi.IsEnglishMode`、`ActivateKeyboardLayout`、`GetKeyboardLayoutName`、`GetCurrentThreadId`、`GetWindowText`、常量 `IME_SMODE_NONE` / `IME_CMODE_FULLSHAPE` —— 全部无调用点，建议删除。

4. **`AutoStart.IsEnabled(exePath)` 的 `exePath` 参数未使用**（`AutoStart.cs:12`），是死参数，删掉或改为校验路径一致性。

## 需实测确认的风险项（非确定性缺陷）

**跨完整性等级（UIPI）**：本程序以标准权限运行时，若前台窗口是**管理员权限**进程（如以管理员启动的 VS Code、任务管理器），`ImmSetConversionStatus` 对该窗口 IMC 的写入可能静默失败。

- `WM_INPUTLANGCHANGEREQUEST` 在 UIPI 消息白名单内，理论上可放行；
- 但 `ImmSetConversionStatus` 不属于消息机制，其跨完整性行为取决于 imm32 内部实现，文档未明确。

建议：在"以管理员运行的窗口"前实测一次。若确认失效，处理方式二选一——(a) README 明确标注该限制并建议以管理员运行本程序；(b) 检测前台进程完整性级别，失效时托盘给出提示。
