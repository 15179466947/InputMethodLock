# Windows 输入法锁定工具 — 完整设计方案

> 版本：v0.6 ｜ 日期：2026-09-06 ｜ 形态：单文件 exe（C# / .NET Framework 4.8）

---

## 1. 项目背景与目标

Windows 用户在中英文混排场景（写代码、用终端、玩游戏、远程运维）中，输入法状态经常被
误触或被系统快捷键（Win+Space / Shift / Ctrl+Space）切换，导致打字错乱。

**目标**：做一个常驻托盘的小工具，把输入法状态"钉死"在指定状态，同时保留临时解锁的逃生口。

## 2. 形态决策：脚本 vs exe

| 维度 | Python 脚本 + PyInstaller | AutoHotkey 脚本 | **C# exe（选定）** |
|---|---|---|---|
| 分发体积 | 30MB+ | 需装 AHK 或打包 ~2MB | **~32KB** |
| 运行时依赖 | 需打包或装 Python | 需 AHK 运行时 | **无（Windows 自带 .NET Framework 4.8）** |
| 杀软误报 | 高 | 中 | 低 |
| IME API 调用 | ctypes 包装，坑多 | 部分 | **P/Invoke 直调** |
| 托盘/热键/自启 | 都要绕 | 热键强 | **原生支持** |
| 后台常驻开销 | 高（解释器） | 中 | **低（<20MB 内存）** |

**结论：exe 形态。** 并且利用系统自带 csc 编译器（`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`），
开发机无需安装任何 SDK，`build.cmd` 一键编译。

### 锁定引擎工作方式

1. `System.Windows.Forms.Timer` 每 **100ms** 检查一次前台窗口：
   - 前台进程在例外列表 → 跳过（自由输入）；
   - 否则按当前模式强制目标状态。
2. **变化监听（`ImeWatcher`，即时响应的主力）**：
   - 低级键盘钩子（`WH_KEYBOARD_LL`）只观察不吞键，监听触发 IME 切换的按键
     （Shift 松开、Ctrl+Space、CapsLock），触发后立即恢复一次、40ms 后再补一次；
   - `SetWinEventHook(EVENT_OBJECT_IME_SHOW/HIDE/CHANGE)` 接收系统 IME 事件
     （含 Win+Space 布局切换），一有变化立即恢复。
3. **为什么以轮询兜底而不是只靠事件**：`WM_INPUTLANGCHANGE` 只发给目标窗口自身，
   跨进程事件源（TSF）实现复杂且部分场景（全屏游戏）收不到；轮询实现简单、覆盖全场景。

### 三种锁定模式的实现

| 模式 | API | 行为 |
|---|---|---|
| **英文锁定** | `ImmSetConversionStatus(hIMC, IME_CMODE_ALPHANUMERIC, ...)` | 保留当前输入法（如微软拼音），只把中英状态钉在英文 |
| **中文锁定** | 见下方专述 | 已是拼音只锁中文；是英文键盘才切一次拼音 |
| **布局锁定** | `PostMessage(hwnd, WM_INPUTLANGCHANGEREQUEST, 0, hkl)` | 只钉住键盘/IME 选择（目标与比较均按完整 HKL，可精确到微软拼音），**其中的中英文模式由用户自行切换**，锁定器不干预转换状态 |

**中文锁定的状态机（v0.5 修复"三段跳"）**：检查前台线程布局的语言 ID（低 16 位）——
是简体中文（0x0804）→ 只调 `ImmSetOpenStatus(true)` + `ImmSetConversionStatus(NATIVE)`，
**绝不动布局**；不是中文且系统装了中文输入法 → 只发**一次** `WM_INPUTLANGCHANGEREQUEST`
切过去，IME 以默认中文模式启动，下一周期再补锁；反复重发切换消息会造成
"英文键盘→拼音英文→拼音中文"的可见抖动，此为 v0.4 的缺陷。

### 第三方输入法（搜狗等）兼容策略（v0.9）

系统标准 IMM32 转换状态写入只有微软系输入法遵守；搜狗等第三方输入法独立维护中英状态，
外部写入通常被无视。检测方式（`IsSystemIme`，按 KLID 缓存）：注册表
`Keyboard Layouts\<KLID>\Ime File` 位于 System32 → 微软内置；否则 → 第三方。

| 模式 | 微软内置输入法 | 第三方输入法（搜狗等） |
|---|---|---|
| 英文锁定（IMM32 应用） | 转换状态写为字母数字 | 关闭 IME（`ImmSetOpenStatus(false)`，同 Ctrl+Space）→ 英文直通 |
| 英文锁定（**TSF 应用**） | **布局级控制**：前台挂输入法布局（HKL 高字 E0xx）→ 强制切美式键盘（v0.10）。TSF 应用无 IMM32 上下文，转换状态通道不存在 | 同左（与品牌无关） |
| 中文锁定 | 转换状态写为 NATIVE | 写入被无视时**模拟 Shift**（`SendInput`，1 秒限速）让输入法自己切 |
| 布局锁定 | 布局级切换，与品牌无关，天然全部有效 | 同左 |

**TSF 应用说明（v0.10/v0.11 定位结论）**：记事本（Win11）、浏览器（Chromium）、资源管理器等
现代应用全部基于 TSF，`ImmGetContext` 返回 NULL——IMM32 的读/写/开关三个手段在这些应用中
统统不存在。且 TSF 时代输入法不走 HKL：搜狗激活时 `GetKeyboardLayout` 仍显示纯键盘布局
（v0.10 的 HKL 检测因此全部误判）。**唯一可靠通道是 TSF 官方 profile 接口**
（`ITfInputProcessorProfileMgr`，src/TsfProfiles.cs，GUID 均对照 SDK 头文件核实）：
`GetActiveProfile` 读真实输入法状态、`ActivateProfile` 直控切换（im-select 同款机制）。
英文锁定的 TSF 分支、快照恢复、中文锁定兜底均已迁移到该通道。

兜底动作全部写 `debug.log`（含前台进程名）便于排查。极端情况（个别输入法连状态读回
都伪装）请使用布局锁定。

### 布局锁定的关键坑（v0.2 → v0.3 修复）

第一版布局锁定用 `ActivateKeyboardLayout`，对其他进程完全无效（该 API 只影响调用线程），
所以 Win+Space 一按就"失效"。正确做法是向**前台窗口**投递 `WM_INPUTLANGCHANGEREQUEST` (0x0050)，
让它自己切换布局；Win+Space 切走后下一个轮询周期会再切回来。

### 其他系统集成

- **状态一致性**：所有开/关操作（托盘左键、菜单、热键、设置保存）统一走 `EnableLock/DisableLock`
  单一入口，任何一处变化实时同步托盘图标、菜单勾选与已打开的设置窗口（v0.4 修复状态漂移）。
  **"下次启动自动启用"（`LockEnabled`）是独立持久偏好**，运行时开关不再写它（v0.5 修复自动启用失效）。
- **启动提示**：启动成功/初始化失败均弹托盘气泡；主入口有异常兜底弹窗（v0.5）。
- **全局热键**：`RegisterHotKey`（消息窗口接收 `WM_HOTKEY`），默认 `Ctrl+~`，必须带 Ctrl/Alt/Shift 修饰键；
  设置中按 Delete 可清除（完全不占用键盘组合）。托盘**左键单击**是免热键的开关入口。
- **停用恢复**：`UnlockLayout` 配置停用锁定时切到的输入法。存储**完整 HKL**（`hkl:XXXXXXXX`，
  如 E0200804=微软拼音）而非语言码——只存语言码会还原成"中文美式键盘"而不是目标 IME（v0.4 缺陷）。
  激活方式同样是向前台窗口发 `WM_INPUTLANGCHANGEREQUEST`。
- **应用图标**：`tools\gen_icon.ps1` 从设计稿生成 256px `src\icon.png`（运行时托盘/窗口图标
  由它高质量实时缩放绘制）与单帧 256px `src\app.ico`（`/win32icon` 嵌入 exe）。
  **ICO 内小于 256px 的 PNG 帧不符合规范**，GDI+ 会渲染成雪花噪声（v0.4 缺陷），故只保留 256 帧。
- **单实例**：命名 `Mutex`（`Local\InputMethodLock_SingleInstance`，仅当前用户会话内互斥，v0.7）。
- **开机自启**：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，免管理员权限。

## 6. 已知问题评估（暂不修改）

### 6.1 英文锁定 × Win+Space 切到微软拼音后"失效"

**现象**：英文锁定生效时，用户按 Win+Space 切换到微软拼音（或其他中文 IME），
之后强制英文不生效/延迟生效。

**原因分析**（三层）：

1. **上下文重建**：Win+Space 切换 IME 时，系统为目标窗口的输入线程重建 IME 上下文（hIMC），
   新上下文默认回到该输入法的**默认转换状态**（微软拼音 = 中文 NATIVE）。这是设计内行为。
2. **TSF 兼容层**：微软拼音是 TSF（Text Services Framework）实现，不是传统 IMM32 输入法。
   我们跨进程调用 `ImmSetConversionStatus` 时经由 IMM32→TSF 兼容层转发，在切换后
   上下文初始化未完成的时间窗内，设置会被忽略或返回成功但不生效。
3. **轮询竞态窗口**：切换完成到下一次轮询之间存在约一个轮询周期的窗口，
   用户手速快时第一个字符会以中文状态打出去。

**结论与建议**：
- **当前定位下是可接受的已知边界**：多数情况轮询会在一个周期内拉回英文；
  切换瞬间的首字符竞态影响小（用户主动切换时本来就有输入意图变化）。
- **若要彻底解决**（按性价比排序）：
  1. 监听前台线程 `WM_INPUTLANGCHANGE` 广播（`SetWinEventHook(EVENT_OBJECT_IME_CHANGE)`），
     切换事件到达时**立即**补一次强制（v0.6 已实现，见 `ImeWatcher`）；
  2. 迁移 TSF：`ITfInputProcessorProfileMgr` 注册激活事件 + 直接激活指定 profile，从机制上根治；
  3. 拦截/禁用 Win+Space（键盘钩子吞掉该组合键）——最暴力，但会改变用户系统习惯，不建议默认开启。
- **决策**：暂不修改，保持现状；若用户反馈切输入法后经常被拉回感到困扰，再实施方案 1。

### 6.2 CapsLock 与微软拼音的英文行为（探讨，未修改）

中文锁定模式下按 CapsLock，微软拼音会切到大写英文直出——这是微软 IME 的内建机制
（CapsLock 默认映射为"英文大写输入"），不属于中英转换状态（Conversion Status）的一部分。

- **是否算问题**：不算。用户按 CapsLock 的意图就是要大写英文，锁定器不应覆盖；
  我们锁的是"默认输入状态"，CapsLock 是显式的临时英文指令。
- **如果要改**：需要低级键盘钩子（`WH_KEYBOARD_LL`）在锁定启用时拦截 CapsLock，
  或注册 IME 的 CapsLock 映射改写——代价是改变用户系统级按键习惯，且全屏游戏钩子稳定性存疑。
- **决策**：保持微软原生行为，不做干预；若后续有需求可作为可选开关（默认关闭）加入"高级选项"。

### 6.3 布局锁定与 Win+Space 的博弈

v0.3 已修复（`WM_INPUTLANGCHANGEREQUEST`）。剩余行为：用户按 Win+Space 后，
布局会在一个轮询周期内被切回——这本身是"锁定"的预期语义。注意 Win+Space 的浮层仍会弹出，
属正常现象。**残余限制**：UWP 全屏独占、管理员权限窗口（UIPI 阻止 PostMessage）下可能锁不住，
后续可加"以管理员运行"选项解决后者。
